## What this repository is

Working directory for **eleyone.fr**, the professional portfolio site of Arnaud ("Eleyone"), a senior PHP/Symfony backend developer. The site is a portfolio and online CV for recruiters, for permanent roles as well as freelance missions, in France and abroad, before April 2027.

The repository holds the Hugo site under construction, the scripts that build and guard it, a BMAD v6.12 skill installation and the project's configuration. The site is produced through the BMAD planning chain (brief → PRD → architecture → stories), not improvised. Planning is done: the brief, PRD, architecture, UX documents and backlog are validated in `_bmad-output/planning-artifacts/`. Stories are delivered one at a time; which ones are done lives in `_bmad-output/implementation-artifacts/sprint-status.yaml`, never in this file.

Git repository. The remote is a private self-hosted Gitea forge (its address is never written in this repository). It is mirrored, since story 1.4, to the **public GitHub repository** `https://github.com/Eleyone/eleyone.fr`, which the site links to as proof of how it was framed and built; the mirror pushes at every push, so anything the forge accepts is public within seconds (`docs/procedures/github-mirror.md`). Treat everything committed as public.

## Public / private boundary

`docs/private/` is gitignored by this repository and never enters its history. It holds the raw source content, the party-mode memory, and `forbidden-patterns.txt`. A fresh clone does not contain it.

`docs/private/` is its own nested git repository, pushed to a separate private repo on the self-hosted forge that must never be mirrored. Commit private changes there explicitly (`git -C docs/private commit`), never through a hook. `git clean -ffdx` in this repository deletes the nested repo; a single `-f` spares it.

- Never commit anything from `docs/private/`, and never copy personal details from it into tracked files: pay or day-rate expectations, city of residence, location and relocation constraints, phone number, interview self-assessment, names of relatives. Public identity is deliberate and allowed: his full name, Arnaud Grousset, his pseudonym "Eleyone", a photo, and "based in France" at country level only. The original photo stays in `docs/private/assets/`; only a resized copy stripped of all metadata (EXIF, GPS) may be committed. Never put his name in `forbidden-patterns.txt`.
- `scripts/check-private.sh` enforces this. It rejects forbidden paths, plus the strings listed in `docs/private/forbidden-patterns.txt`. An alert shows only where a match is (commit, file, line) and the line number of the pattern, never the matched content or the pattern itself. In a worktree or clone without `docs/private/`, set `PRIVATE_PATTERNS_FILE` to the pattern file: a paths-only run is not an audit (`docs/procedures/check-private.md`). Enable the local hook once per clone with `git config core.hooksPath .githooks`. Audit the full history with `scripts/check-private.sh history`, and run it before any push to GitHub: a commit pushed there stays reachable by SHA even after a force push.
- The same script runs on the forge as a `pre-receive` hook, installed in story 1.2 (`docs/procedures/gitea-pre-receive-hook.md`): it is the authority, since the mirror pushes from the server. It refuses forbidden paths, `.env` and its suffixed variants, image extensions (until C20 runs in the hook, story 5.4), `assets/cv/*.pdf` (until C21 does), any path that repeats a pattern, any pattern in a file's content, and any pattern in a commit message. Copy the script to the forge again whenever it changes.
- Public planning artifacts cite the published site pages, not the raw cases.

## Decisions taken (2026-09-13)

These supersede the original brief. The validated brief, PRD, architecture, UX (`DESIGN.md`, `EXPERIENCE.md`) and backlog (`epics.md`) are in `_bmad-output/planning-artifacts/`; the implementation readiness decisions D-1 to D-17 (2026-09-13) are applied to them.

- **Purpose and brand:** eleyone.fr is Arnaud's portfolio and CV. "Ton Pote le Geek" already exists and is only mentioned or linked, not developed on this site.
- **Languages:** French and English, both complete. English is a full version aimed at international recruiters, not a subset.
- **Generator:** Hugo (native multilingual, single binary, no dependency tree). Build output is served by an nginx container on existing Docker infrastructure behind a reverse proxy.
- **URLs:** French at the domain root, English under `/en/`. No automatic redirect based on browser language.
- **Diagrams:** D2, one shared `structure.d2` per diagram plus `fr.d2`/`en.d2` label entry points, ELK layout, rendered with `--omit-version`. SVGs are committed and CI regenerates them and fails on any diff; the D2 version is pinned. See the `experiment/d2-bilingue` branch.
- **Chiliz cases (02, 03, 04):** one page, one "Contexte mission" box per section. Each case is its own file; the page assembles them (`group: chiliz`) and must render with only the published sections.
- **Videos:** plain links to unlisted YouTube videos. No iframe, no cookie banner.
- **No small-business offer page:** the presentation mentions the automation side activity with a link to Ton Pote le Geek; case 01 was done under it.
- **Quality targets:** zero JavaScript in v1 where possible, WCAG 2.2 AA, Core Web Vitals "good" thresholds on mobile, a per-page weight budget. Checked with scripts rather than Chrome/Node tooling.
- **Planned live material** is invisible in production and shown only in the draft build.
- **Release:** a base (home page as the CV, about, contact, legal pages, and cases 01, 02 and 05 under their positions) first, then the remaining cases one at a time.
- **CI and hosting:** the main forge is a private Gitea on a homelab (x86_64 Actions runners), separate from the production server that will serve the site. The homelab can go down at any time; it is never exposed publicly. Gitea runs checks, pull requests, image build and deployment. GitHub is the public mirror and runs **checks only**: no image build, no deployment. Both CIs call the same scripts (`scripts/check.sh` and the shared checks job, AD-10/AD-11). The public/private guard runs in a Gitea pre-receive hook (story 1.2); a control that lives only in CI arrives after the mirror has published, so C20 and C21 belong in that hook too.
- **Repository:** public on GitHub, including BMAD planning artifacts, because showing the framing process is part of the point. No private files, no raw cases.
- **Tooling:** the right tool for the job. Plain scripts rather than heavy tooling in CI or build images; no Symfony or React for a static site.

Pilot case: `content/cases/chiliz/case-02-chiliz.{fr,en}.md` follows `docs/format-cas.md` (v0.4: grouped cases live in their group's folder, and each case points to its career position with the `position` key, whose identifiers are frozen in AD-18) and is the architecture's test fixture. The stack vocabulary lives in `data/stack.yaml`. The validated architecture is in `_bmad-output/planning-artifacts/architecture/`.

Unchanged constraints: static site, Markdown content editable without touching code, no database, no backend to maintain, sober and readable design, simplicity over everything. Out of scope for v1: blog, client area, contact form, advanced analytics.

## Development workflow (decided 2026-09-13)

1. **Branches, linear history, no merge commits.** Work on a branch cut from `dev`, named `feat/*` (feature), `fix/*` (bug fix), `chore/*` (tooling, configuration, sprint tracking) or `docs/*` (documentation only), then open a PR to `dev` (squash). **A branch that delivers a story carries that story's number**, as `<prefix>/<epic>-<story>-<slug>` — `feat/7-4-publish-cv-pdfs`, not `feat/publish-cv-pdfs`. It is not cosmetic: `verify-and-merge-pr` reads the story from the branch name (`scripts/lib/sprint.sh`, `^[a-z]+/([0-9]+)-([0-9]+[a-z]?)-`), and without it the review gate cannot recognise the head commit as the status commit point 4 allows, so two gates block on a correct PR. Story 7.4 cost a closed PR, a new one and a replayed review for this alone (epic 7 retrospective, 22/09/2026). A branch that delivers no story — a retrospective fix, a procedure — carries no number. The prefix changes no gate: the documentation exception depends on the files a PR touches, not on its branch name. Releases bring `dev` into `main` by **rebase, never a merge commit** (fast-forward: `main` must stay an ancestor of `dev`), tagged `vX.Y.Z` on `main`. A **production hotfix** uses a `hotfix/*` branch cut from `main` (a prefix reserved for such branches; `fix/*` only targets `dev`), goes back into `main` (fast-forward), then `dev` is rebased onto `main` and pushed with `--force-with-lease`; every open PR to `dev` is then rebased and reviewed again, since its review report points to a rewritten SHA. The `hotfix` skill may run that force push only after Arnaud's explicit approval at that moment; never cherry-pick a hotfix into `dev` (a copied commit breaks the next fast-forward). `dev` and `main` are protected on Gitea: nobody pushes or force-pushes to `main`; Arnaud's account is in the push list of `dev` because Gitea only allows a force-push from an account that can already push, so a direct push to `dev` is forbidden by procedure only. Gitea sets merge styles per repository, not per branch: the repository allows only squash and fast-forward only, a PR branch is updated by rebase only, and the scripts choose the style from the PR base. The settings and how to check them through the API are in `docs/procedures/gitea-branches.md`. `main` is the default branch on the GitHub mirror and is never rewritten; `dev` is the working branch. A GitHub ruleset lets only the mirror identity write to the public repository.
2. **Code review by another LLM is mandatory before any merge.** The reviewer comes from a different vendor than the author (code written by Claude → reviewed by Gemini through the `agy` CLI in `--mode plan` without `--dangerously-skip-permissions`, so every shell command is refused to it (with that flag, a plain `grep` read a `.env`); plan mode is still not read-only (it has created files in its review copy), so only the isolated copy protects the repository; code written by Gemini → reviewed by a Claude model). The review runs in a **temporary export of the reviewed commit outside this repository** (`git archive`, with no `.git`, whose `gitdir` line would give the reviewer this repository's path), so the external reviewer can never read `docs/private/`; `scripts/check-private.sh` runs on the reviewed scope first, and every file the reviewer adds, changes or deletes in the copy is reported. The report is a Gitea PR comment whose first line is `llm-review sha=<SHA> base=<base> model=<model> verdict=<pass|block>`; it is never committed. Reviews run through `scripts/llm-review.sh`, in two stages: every story starts with a spec review (`--story <n.m>`: adversarial, structure and prose lenses on the story text), and every PR gets a code review (`<PR number>`: edge-case-hunter and verification-gap lenses plus the project layer). In both, the reviewer applies the BMAD `bmad-review` skill; the author never reviews in its place. Each story has a story file, `_bmad-output/implementation-artifacts/<story-key>.md`, whose `Status:` line matches `sprint-status.yaml` and whose "Revue de spec" and "Revue du code" sections record every finding with its decision; deferred findings go to `deferred-work.md`.
3. **Documentation exception.** A PR whose files are all under `_bmad-output/` (planning artifacts and sprint tracking, `sprint-status.yaml` included) needs green CI only, or the bootstrap substitute while CI does not exist. The exception never covers any other file, including `content/**`, `AGENTS.md`, `CLAUDE.md`, `docs/procedures/**`, `.claude/**` or `docs/format-cas.md`.
4. **Merge gates.** Nothing is merged without a review report on the head SHA with a non-blocking verdict, the public/private guard passing, green CI once CI exists, and a consistent sprint status (statuses only in v1). The release PR `dev` → `main` meets the review gate when every commit in `main..dev` is the squash of a PR merged by `verify-and-merge-pr`, and `release` merges only with an explicit `--merge` run by Arnaud. **A story PR to `dev` is merged by the agent itself** as soon as the five gates pass (Arnaud's decision, 18/09/2026): the audit proves what a second opinion would only repeat, and he is asked to arbitrate content and design, not to countersign a green audit. The release PR `dev` → `main` and a hotfix's `--force-with-lease` still wait for his approval at that moment. **Sprint status lives in the story's own PR:** the story's line in `sprint-status.yaml` and the `Status:` line of its story file move to `in-progress` in the branch's first commit, to `review` in a commit made before the LLM review, and to `done` in a commit made after a passing review, just before merge. The review gate therefore accepts a report on the parent of the head SHA when the head commit is that single status commit: it changes only `sprint-status.yaml` (the story's line from `review` to `done`, `last_updated`, and the epic's line when the story closes its epic) the story file's `Status:` line (from `review` to `done`), and otherwise only adds lines to the story file and to `deferred-work.md` (review reports, the author's decision on each finding, deferred findings), checked line by line. Any other change after the review requires a new review.

5. **Secrets.** Every token, credential or secret the project needs (Gitea API token, legal values, anything else) is defined in `.env` at the repository root, which is never committed: it is gitignored and rejected by `scripts/check-private.sh`. `.env.example` lists the variable names without values. Scripts load `.env` without printing any value; agents never print or copy a secret value into files, commits or conversation output. In CI, the legal values are Gitea secrets under the same names; the `GITEA_*` API variables stay on the dev machine only, because Gitea rejects secret names starting with `GITEA_`, and CI jobs use their built-in token instead.

6. **Bootstrap rule** (until CI and the epic 0 skills exist). The CI gate has three states, `pass`, `fail` and `absent`; `absent` is accepted only while `.gitea/workflows/checks.yaml` does not exist on the base branch, which the script detects without a manual switch, and it blocks once that file exists. Meanwhile, `scripts/check-private.sh history`, then also `scripts/check.sh` once it exists (story 3.2), run on the head SHA by `scripts/verify-and-merge-pr.sh`, which shows the CI gate as `absent` with the substitute's result. Sprint planning runs before story 0.1, and the PR adding `sprint-status.yaml` is the only one merged without the sprint gate. Before `llm-review` exists, run `agy --mode plan` by hand in a temporary git worktree outside the repository and paste the report as a PR comment in the format above; Arnaud merges by hand.
7. **Anticipation.** A story may add the minimum another story owns when nothing builds without it, and then it writes its scope: the story file and a comment in the file itself name the owning story **and** exactly what the anticipation touches. A stub that named what it did and refused the rest was completed without harm; a cascade whose scope was left unsaid hid a page and had to be undone two stories later (epic 2 retrospective, 17/09/2026).
8. **A document is read whole, not as a diff.** A story that edits a long document re-reads it end to end before committing, and reviews the file, not only its hunks. Two failures in epic 4 came from the same blind spot: `epics.md` accumulated four partial copies of epics 0–4 over six stories — two pure insertions, no deletion, each story writing into a different copy until none was complete — and `build-image.md` stated both that the nginx configuration was absent from the image and that it replaced the default. No gate reads a document as a whole: `sprint-consistency` reads `sprint-status.yaml`, `check.sh` reads the rendered site, a review reads a diff, and +1713 lines of plausible backlog read as added detail. `scripts/tests/test-docs-headings.sh` now refuses a repeated level-1 or level-2 heading, which catches a duplicated document but not a stale sentence. **A story that makes a future-tense sentence true puts it in the present tense in its own PR** — the same rule the epic 1 retrospective asked for and which epic 4 proved had never taken (epic 4 retrospective, 21/09/2026).
9. **A guard gets a test that fails without it.** The project already demands this of a control; it was never extended to the *guards* inside scripts, and five of them in three epics guarded nothing — a `|| true` that swallowed grep's errors, an empty-list guard that never fired, a `\$request[^_]` rule that let `$request_uri` through, a repository check defeated by a symlink, and an image selection defeated by a filename git quotes. All five read as plausible; none was found by review. **The test must exercise the input the guard is meant to refuse**, not only one it accepts, and it must be run once with the guard removed to see it fail (epic 5 retrospective, 21/09/2026).
10. **A rule that describes a tool's behaviour is true only once verified.** AD-19 said to look for the string `GPS` in an image's bytes — a photo carrying real coordinates contains no such string, they live in binary inside EXIF — and prescribed Hugo's `crop` where it described `fill`. Both read perfectly and were false. Before writing a tool's behaviour into an architecture decision, run it (epic 5 retrospective).
11. **A measurement on today's content says nothing about tomorrow's.** A case link measured 44 px because the only existing case has a long title; with a short one it is 22 px, below the WCAG target. Measure the short case, the empty case and the long case, not the one that happens to exist (epic 5 retrospective).
12. **When the solution changes mid-story, the spec you just wrote gets re-read.** Point 8 asks that a document be read whole rather than as a diff; it does not cover the case where *you* make your own sentence false two hours after writing it. Two acceptance criteria in consecutive stories demanded the opposite of what their story shipped — 6.2's said "case number in the margin" while the page stacks it, 6.3's said "from `baseof.html`" while five templates call the partial. Both were found by the same review lens, never by the author. A story that rewrites its spec up front revisits that spec when the approach turns (epic 6 retrospective, 22/09/2026).
13. **A reversal ends with a sweep of what the old approach left elsewhere.** The material half of point 12. The same turn left a dead CSS rule carrying a comment that contradicted the page, and left `links.sh` behind when `html.sh` gained the two render roots — so the back-to-career rule that story 6.1 had just added ran on **no case page at all**. The place you edited is not the only place the old approach reached (epic 6 retrospective).
14. **A position has two axes, and a sticky layout is verified by scrolling.** The table of contents was checked at x = 45, the margin column, and declared correct; it was occupying a grid *row*, so the content fell below it and 768 px of text column sat empty beside it. And the rubric numbers overlapped the sticky toc — four collisions — which no still measurement can show. Measure both axes, and scroll (epic 6 retrospective).
15. **A control written by the author of the code it guards inherits its blind spot.** C24 and the typography partial both treated the plain space as the only possible fault; a wrong U+00A0 where the design wants U+202F came out "composed" and false, and neither saw it. When the code fixes a fault, the control asks what *other shapes* that fault can take (epic 6 retrospective).
16. **A fixture declares what the real page declares.** A test fixture without `<meta charset>` made `xmllint` read it as Latin-1; the UTF-8 patterns stopped matching and the control would have passed green. A fixture that does not resemble the real output turns a control into decoration (epic 6 retrospective).
17. **Dev machine prerequisites.** `jq` (installed); `poppler-utils` — `pdftotext` and `pdfinfo`, which C21 needs and which the local pre-commit runs, so a clone without them refuses to commit a CV PDF until they are installed (story 7.1); `agy`, authenticated, with `agy models` answering; Docker, available natively (the dev machine is a native Linux, not WSL: an earlier version of this file described a WSL layout and a symlink that do not exist — verified, epic 7 retrospective); Hugo and D2 installed locally by `scripts/ci/install-tools.sh --local` into the git-ignored `.tools/`, with versions read from `tools.env` only. A distribution package is declared here rather than installed by `install-tools.sh`, which places pinned binaries from archives, not packages (Arnaud's decision, 22/09/2026).
18. **A finding of a known error class is a sweep order, not a line to patch.** Story 7.1 took six review rounds and five blocking verdicts, and every one was a variant of the same question — *what does this condition not see?* A `grep` whose exit code was read as "not found" was fixed on one line while its twin sat three lines below; the non-ASCII path hole the epic 5 retrospective had closed in the guard reopened untouched in a new script written seven days later. So: when a review names an error class, the fix **starts** by searching the whole change for other instances of that class, and a finding about a *trigger condition* is answered by re-enumerating everything that condition lets through — not by adding the one case cited (epic 7 retrospective, 22/09/2026).

19. **A lesson does not carry itself into the twin file.** The material half of point 18, and the one that keeps winning. `scripts/lib/image.sh` holds the single list of image extensions precisely because two copies once let a file slip past C20 — its own header says so. `scripts/lib/pdf.sh`, written as its twin, has no list at all, and the two CV names ended up in four files under four spellings. Point 9 asks a guard for a test; point 16 asks a fixture to resemble the real output; neither asks what the *sibling* already learned. When a file is written "like" another, walk the older one guard by guard and say, for each, whether the new one needs it — intention is not symmetry (epic 7 retrospective). **And the walk is written down, or it does not happen.** Epic 9 proved that knowing this rule is not applying it: story 9.3 wrote *"a fix in one place does not carry itself, points 18 and 19"* into `scripts/tests/test-contact-page.sh:57`, and story 9.4 then wrote that file's twin without taking its guard — `test-contact-page.sh:137` builds the site **without** its page and checks the link disappears; `test-about-page.sh` never does. Three of the four aggregate findings of that epic were this same point. So a story that writes a file "like" an existing one names the elder in its story file and lists its guards, saying for each whether the younger needs it. Three lines is the whole cost (epic 9 retrospective, 24/09/2026).

20. **Every finding gets a written decision — including the ones you refuse.** A reviewer told story 9.2 it had failed to add an entry to `docs/CHANGELOG.md`. That file does not exist here and no rule of this project asks for one — but the rule is **real**: it lives in the reviewing account's own global memories, where it describes a different project of Arnaud's, one whose CI generates a changelog. **The external reviewer carries its user's global instructions into this repository's isolated review**, so a verdict can block on a contract this project never signed; that is the same class as the reviewer not seeing the repository, and it is refuted the same way — by naming where the rule lives and why it does not apply here. Checking `AGENTS.md`, `docs/` and the architecture is not enough to call a rule invented, and this point said "invented" until a later review proved otherwise. The story was right to ignore the finding and wrong to leave no trace — a finding with no recorded decision is indistinguishable from a finding nobody read, and the next reviewer raises it again. One did, in story 9.6, three times across three reports, noting itself *"already reported, still present"*, and no decision was ever written. So the story file records **every** finding with its disposition: retained, refuted on evidence (with the evidence), deferred to `deferred-work.md`, or invalid because the rule it invokes does not exist (with what was checked to establish that). Silence is not a decision. **A PR that has no story — a retrospective's actions, a procedure, tooling — records the same thing on the pull request itself**, in its body or, once it is open, in a comment, since that is the only place a reader of that change will look. `create-pull-request.sh` writes a body only at creation and never updates it, so decisions taken after the first review land in a comment; the case came up in the very PR adding this point (epic 9 retrospective, 24/09/2026).

21. **A story's noisy loop runs in a sub-agent; the cross-cutting judgement does not.** Build logs, 534 test cases, browser measurements and eight review rounds fill the orchestrating context with material that has no value beyond the story producing it — and that context ran out mid-session during epic 9. So the implementation loop is delegated: the sub-agent writes the code and the tests, runs the suite and the controls inside `CHECK_IMAGE`, and iterates on the review's findings. What stays with the orchestrator is what a fresh agent cannot do, and what epic 9 showed actually fails: the spec-review triage, the arbitrations put to Arnaud, **the twin-file brief of point 19 — named explicitly in the sub-agent's prompt, because it cannot derive which sibling to walk** — the verification of the sub-agent's report against the repository, and the merge.

    Two things this is *not*. It is **not** a remedy for forgotten rules: measured across epic 9, the first story took seven blocking verdicts with the freshest context and the last took none with the fullest, and all four of that epic's aggregate findings were files never opened rather than rules forgotten — isolating a story makes that worse, not better, which is exactly why the brief is the orchestrator's job. And it does **not** extend Arnaud's merge delegation of 18/09/2026: that decision named the agent whose own audit proves what a second opinion would repeat. The orchestrator re-runs the five gates itself on work it did not write, and merges (Arnaud's decision, 24/09/2026).

    A sub-agent's report is an unverified claim, never an established fact. Before it becomes a merge argument, reopen the file, the commit, the test output.

The dev skills (`llm-review`, `create-pull-request`, `verify-and-merge-pr`, `sprint-consistency`, `check-private`, `rehearse-release`, `release`, `hotfix`, `publish-case`) follow the three-level pattern `.claude/skills/<name>/SKILL.md` → `docs/procedures/<name>.md` → `scripts/<name>.sh`. Each skill must be available whatever the agent harness: its folder lives in `.claude/skills/<name>/`, and `.agents/skills/<name>` and `.agent/skills/<name>` are relative symlinks to it (read by Antigravity, Gemini CLI and harnesses following the `.agents/skills/` convention). One copy only, so nothing drifts; a BMAD reinstall does not delete skills it did not write. They are built in epic 0 of the backlog, except `publish-case` (story 3.17) and `release`, `rehearse-release` and `hotfix` (epic 11), which come after the stories they rely on; until they exist, apply these rules by hand under the bootstrap rule (point 6). Every script follows `docs/procedures/shell-scripts.md` (rules and known shell pitfalls); shared logic lives in `scripts/lib/`, and `scripts/tests/run.sh` replays the scripts' offline tests before any PR that touches `scripts/`, on the dev machine and in CI (story 3.12).

## BMAD workflow

Skills are installed in `.claude/skills/`, with mirrored copies in `.agent/skills/` and `.agents/skills/` for other agent runtimes. The project's own dev skills are symlinks in those two folders, not copies (see Development workflow). Invoke them as slash commands (`/bmad-help` recommends the next one). The expected chain for this project: Analyst brief → PM PRD (v1 then v1.1) → Architect (repo layout, Docker nginx build pipeline, Markdown and D2 naming conventions) → small stories delivered one at a time.

Arnaud's stated preference: before each story, restate your understanding and ask questions. He would rather field one question too many than redo a page. From story 0.6 on, the spec review (`scripts/llm-review.sh --story <n.m>`) comes first, and the restatement and questions build on its triaged findings.

**An arbitration offers the full range of options, not the comfortable one.** Story 4.1 asked him where the release legal-values file should live and offered only locations outside the repository, never `docs/private/` — which satisfies the same constraint while versioning and backing the file up. He found it himself by asking a question, and it cost a PR. The options an agent has already discarded belong in the question, with the reason they were discarded, so he arbitrates on the real field (epic 4 retrospective, 21/09/2026).

**A retrospective action whose deadline is a future story is written into that story.** Three epic 0 actions were deferred "to their deadlines" and nothing but the retrospective document tracked them. One deadline passed unnoticed — seven days of spec reviews ran without the ranking the story 0.5 criterion demands. One was met by accident: the spec review of story 3.16 independently rediscovered the same finding. Only the third is now somewhere it will be read, in the text of the story it conditions. The list tracks *that* the action is in the story, not what it says (epic 0 actions reviewed, 22/09/2026).

**An open question is tracked like an action, or it is lost.** The fix above was applied to retrospective *actions* and never to the **open questions** the same documents end on. The result, measured at the epic 9 retrospective: fifty-two actions, every one `done` and every one traceable to a file and a line — and, beside them, open questions living in prose alone, which no line of `sprint-status.yaml` carried and no gate would ever raise. One of them had already passed its moment with nothing to catch it. So a retrospective's open questions go into `open_questions:` in `sprint-status.yaml`, each with the epic that raised it and where its answer will land — a story, a `deferred-work.md` entry, or an arbitration to put to Arnaud. A question with no landing place is the one to worry about, and writing it down is what makes that visible (epic 9 retrospective, 24/09/2026).

### Configuration

Config is a four-layer TOML merge. `_bmad/config.toml` and `_bmad/config.user.toml` are installer-managed and regenerated on every install — never edit them. Durable overrides go in `_bmad/custom/config.toml` (team) or `_bmad/custom/config.user.toml` (personal, gitignored); per-skill overrides go in `_bmad/custom/<skill-name>.toml`. The installer never touches those.

Key values: project `eleyone.fr`, user `Eleyone`, output folder `_bmad-output/`, planning artifacts in `_bmad-output/planning-artifacts/`, implementation artifacts in `_bmad-output/implementation-artifacts/`, project knowledge in `docs/`, skill level `intermediate`. `_bmad/custom/bmad-party-mode.toml` moves party-mode memory and keepsakes into `docs/private/party-mode/`.

**Language:** talk to Arnaud in French. Planning documents are written in French too (`document_output_language` is overridden to French in `_bmad/custom/config.toml`). Code is in English: identifiers, front matter keys, file and directory names. Site content exists in French and English.

**Case content format:** `docs/format-cas.md` is the contract every case file follows: one file per case per language, English front matter keys, fixed FR/EN headings, `[TODO: …]` markers for anything missing.

### Scripts

Python helpers run through `uv` (a `.venv` with Python 3.14 is present). Run each from the exact path written in the skill, never assume co-location.

```bash
uv run _bmad/scripts/resolve_config.py --project-root .          # merged config as JSON
uv run _bmad/scripts/resolve_customization.py --skill <skill-root> --project-root . --key workflow
uv run _bmad/scripts/memlog.py append --workspace <ws> --type decision --text "<one-line gist>"
scripts/check-private.sh history                                 # audit history for private content
```

`memlog.py` is the only sanctioned writer for `.memlog.md`, a workflow run's append-only memory and audit trail. Anything not logged there is lost when a session resumes.
